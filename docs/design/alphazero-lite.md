# AlphaZero 风格小模型路线（设计说明）

## 文档信息

- **项目**：zen-gomoku（产品仓）+ 独立训练仓（拟名 `zen-gomoku-ml`，待建）
- **状态**：设计草案（**未开发**）；确认本文件后再拆 Issue、再写代码
- **读者**：深度学习零基础、希望循序渐进落地的协作者
- **前置决策**（已确认）：
  1. 训练代码放**新仓库**，产品仓只接入推理与模型产物
  2. 产品支持两套规则：**自由五子**（无禁手）与 **禁手**（中国规则子集）；**各训各的模型**，不混用
  3. 工程顺序：**先落地禁手能力**（与自由模式并存），再按规则分别生成老师棋谱并训练
  4. 算法路径：每种规则都是 **先模仿唐僧，再（可选）自对弈闭环**

相关现状见 [ai-agents.md](./ai-agents.md)、[functional-spec.md](../requirements/functional-spec.md)。

## 1. 用白话说清在做什么

现在游戏里的「唐僧」靠程序员写的打分 + 搜索下棋。  
接下来要为**两套规则各做一个**「会看棋盘猜下一步」的小神经网络（共两个模型文件，互不替代）。

整条路可以想成：

```txt
① 游戏支持「自由 / 禁手」两种规则（禁手为新增；自由保持现状）
        ↓
② 分别用唐僧在对应规则下下棋，攒两套「老师题库」
        ↓
③ 分别训练两个小网络：自由模仿模型、禁手模仿模型
        ↓
④ 对弈时按当前规则加载对应模型（推理）
        ↓
⑤ （可选）各自做自对弈，争取超过各自的老师
```

**重要：** 自由模型只在自由规则下用；禁手模型只在禁手规则下用。  
换规则 ≈ 换游戏，**不能**指望一个模型两套规则通用（至多当临时实验，不作为产品默认）。

- **训练**：在电脑上用 Python 完成（新仓库），得到**两份**模型文件。
- **推理**：在浏览器（及以后小程序适配层）里按规则加载对应模型；**不在网页里训练**。

## 2. 目标与非目标

### 2.1 目标（本路线）

| 阶段 | 目标 | 验收直觉 |
| ---- | ---- | -------- |
| R0 | 禁手接入产品；与**自由模式并存**（可切换） | 两套规则落子/胜负正确；禁手非法点不可下 |
| R1 | 唐僧在**自由、禁手**下均可对弈并导出棋谱 | 能分别批量生成两套老师棋谱 |
| R2 | 训练并导出**两个**模仿模型（自由 / 禁手） | 各自评测：模仿命中率；对猪八戒量级不崩 |
| R3 | `AlphaZeroAgent` 按当前规则加载对应模型 | 人机可选小模型对手；规则切换换模型 |
| R4 | （可选）两套规则各自自对弈闭环 | 各自新旧模型擂台胜率明显 > 50% |

### 2.2 非目标（本阶段不做）

- 职业级 Renju / 击败顶尖专业引擎（如需另立项、另算力）
- 完整企业级 MLOps（K8s、在线特征平台等）
- 在小程序内直接训练；小程序推理以适配层为准（本地或云端）
- 用本路线默认「一定能拿发明专利」（见文末知识产权说明）

## 3. 两套规则、两个模型

### 3.0 纠正常见误解

| 说法 | 是否正确 |
| ---- | -------- |
| 「先做禁手，所以只训禁手模型、自由不训」 | **不对**（旧草案易被理解成这样；已作废） |
| 「要训两个模型：自由一份、禁手一份」 | **对**（当前决策） |
| 「一个模型同时覆盖两种规则」 | **不做默认目标**（数据分布与合法点不同） |

### 3.1 规则口径

| 规则 ID（草案） | 含义 | 禁手 |
| --------------- | ---- | ---- |
| `freestyle-v1` | 自由五子（现状） | 无；五连即胜（长连亦胜，与现实现一致） |
| `renju-cn-v1` | 中国规则子集 | **仅黑**：三三、四四、长连；细节盘例另文 + 单测 |

### 3.2 为何工程上仍「先做禁手能力」

- **自由规则已在线上**，老师 Agent（唐僧）已可在自由下下棋。  
- **禁手是新增能力**：产品、走法生成、棋谱导出都要先能跑禁手，才能攒禁手老师题库。  
- 训练仓用同一套流水线，用 `rules=` 参数分两趟跑：先/后顺序可调，建议 **先自由模仿跑通闭环，再复用脚本训禁手**（降低第一次踩坑成本）。

```txt
产品：自由模式（已有） + 禁手模式（R0 新增）──并存可切换
训练：pipeline(rules=freestyle) → model-freestyle.onnx
      pipeline(rules=renju-cn)  → model-renju.onnx
对弈：当前规则 === freestyle ? 加载自由模型 : 加载禁手模型
```

### 3.3 对现有四级 AI 的影响

- **自由模式**：沙和尚～唐僧行为与现网一致（可继续作为自由老师）。  
- **禁手模式**：落子校验 + 走法生成必须过滤黑方禁手点；唐僧在禁手下的棋谱才当禁手老师。  
- 规则变更（改禁手定义）→ **只重训对应规则的模型**。

### 3.4 产品策略

- UI：**规则切换**（自由 / 禁手）；切换时清空重开，避免半盘换规则。  
- 棋谱元数据带 `rules` 字段，加载时校验，禁止串规则复盘当训练数据。  
- 小模型对手：展示名可区分，如「小模型（自由）」「小模型（禁手）」，或随当前规则自动选用。

## 4. 双仓库职责

| 仓库                      | 职责                                                                            | 不放什么                       |
| ------------------------- | ------------------------------------------------------------------------------- | ------------------------------ |
| **zen-gomoku**（本仓）    | 禁手规则（`core`）、四级 AI 适配禁手、`AlphaZeroAgent` 推理、ONNX/WASM 加载、UI | 大规模自对弈、PyTorch 训练循环 |
| **zen-gomoku-ml**（新仓） | 用老师 Agent 生成棋谱、数据集、训练脚本、导出模型、离线对战评测                 | Vue 页面、Pinia                |

**交接物**（至少两份，规则绑定）：

| 产物示例 | 绑定规则 |
| -------- | -------- |
| `gomoku-imitate-freestyle-v0.1.onnx` | `freestyle-v1` |
| `gomoku-imitate-renju-v0.1.onnx` | `renju-cn-v1` |

另附：输入输出约定（张量形状、通道含义、坐标映射）+ `rules` 版本说明。

规则判定逻辑优先：

1. 在本仓 `src/core/` 用 TypeScript 实现并单测；或
2. 抽成双方都能引用的「规则说明 + 测试用例」，训练仓用 Python **复刻同一判定**并跑同一套用例。

**禁止**两边各写一套互不一致的禁手。

## 5. 算法两阶段（循序渐进）

### 5.1 Phase A — 模仿唐僧（监督学习，每种规则各跑一遍）

对 `freestyle-v1` 与 `renju-cn-v1` **分别**：

1. 用唐僧（或同级搜索）在该规则下对弈，导出棋谱。  
2. 样本：`(棋盘特征, 老师落子)`；可选终局胜负标签。  
3. 训练小网络；导出对应 ONNX。  
4. 本仓按当前规则加载对应模型；选最大概率**合法**点（禁手下须再滤禁手）。

建议顺序：先跑通 **自由**（规则已稳）→ 再跑 **禁手**（复用同一训练脚本）。

**成功标准（每种规则各自）**：测试集 Top-1 / Top-3 命中老师着法达约定阈值；对猪八戒量级不崩。

### 5.2 Phase B — 自对弈闭环（可选；仍按规则分开）

每种规则独立自对弈、独立擂台，**不要**用自由自对弈数据去更新禁手模型（反之亦然）。

Phase B 在该规则的 Phase A 与本仓推理稳定后再开。

### 5.3 与现有 `IAgent` 的关系

```ts
// 仍统一接口；四级对手保留，小模型作为额外难度或独立选项
interface IAgent {
  readonly name: string
  getNextMove(board: number[][]): Promise<AiMove | null>
}
```

搜索树 / 神经网络会话**不进 Pinia**；Store 只持有 Agent 实例与难度标识。

## 8. 知识产权与成果形态（建议，非法律意见）

结合常见公开资料（软著登记制 / 发明专利实质审查 / 学术论文发表），以及「本项目以学习与产品化为主」的定位：

| 形态                | 难度（相对） | 保护/价值                                  | 对本项目的贴合度                                          |
| ------------------- | ------------ | ------------------------------------------ | --------------------------------------------------------- |
| **软件著作权**      | 低           | 保护代码表达；申报、上架、教学演示「有证」 | **优先、性价比高**                                        |
| **技术/教改类论文** | 中           | 讲清工程复现、教学链路、评测；不替代专利   | **适合写「可复现教学案例 / 工程实践」**                   |
| **发明专利**        | 高           | 保护技术方案；周期长、要三性               | **不要默认能授权**；需明确区别于公开 AlphaZero/五子棋先验 |

**为何说「论文或软著通常更容易一些」：**  
软著以形式审查为主，材料齐较易下证；论文取决于选题与投稿渠道，但不要求专利意义上的「创造性三性」。发明专利对「又一个 AlphaZero 五子棋」类方案先验极多（含禁手 Renju + 神经网络 + MCTS 的开源与论文），单纯复现很难构成有竞争力的权利要求。

**若仍想冲专利，产品/技术可往这些方向「长出差异点」（示例，需代理评估）：**

- 绑定**具体技术问题**：如浏览器/教学机时延与包体约束下的推理与搜索调度，而不只是「下棋更强」。
- 绑定**禁手规则下的数据与校验一致性**：双语言同测用例、规则版本化与模型绑定的方法。
- 绑定**教学场景**：从「模仿教师 Agent → 学生可对照解释」的训练与对弈方法（需写出可实施步骤与效果，而非纯业务描述）。
- **开源/公开演示之前**完成检索与申请评估；过程中保留发明笔记（日期、问题、对比实验）。

**与个人目标的匹配建议：**  
更务实的组合往往是：**软著（产品确权）+ 一篇可复现的工程/教学实践文（简历与课研故事）**；专利仅在出现清晰、可写进权利要求的技术差异后再单独立项，避免拖慢学习主线。
